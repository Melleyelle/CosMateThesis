## 0. ภาพรวมระบบ

CosMate มีผู้ใช้ 2 กลุ่ม ซึ่งใช้งานต่างกันชัดเจน

| ผู้ใช้ | ลักษณะ | อุปกรณ์หลัก | สิ่งที่ทำ |
|---|---|---|---|
| **ลูกค้า** | อายุ 18–35 ปี ส่วนใหญ่ไม่เคยเช่าชุด จองตามวันงาน | มือถือ | ค้นหาชุด เลือกไซส์และวัน จอง ชำระเงิน ติดตาม ส่งคืน รีวิว |
| **พนักงานร้าน (แอดมิน)** | ทำงานเป็นคิว ต้องไม่พลาดเส้นตาย | คอมพิวเตอร์ + กล้อง | ตรวจบัตร ตรวจสลิป แพ็กส่ง รับคืน ตรวจสภาพ คืนเงิน จัดการสต็อก |

หลักคิดที่ใช้ทั้งระบบมี 3 ข้อ

1. **ฐานข้อมูลเป็นผู้ตัดสิน หน้าเว็บมีหน้าที่แสดงผล** ยอดเงิน วันว่าง และสิทธิ์ทุกอย่างคำนวณและตรวจซ้ำใน Supabase เสมอ หน้าเว็บคำนวณซ้ำเพื่อแสดงตัวเลขล่วงหน้าเท่านั้น
2. **ลูกค้าเห็นตัวเลขจริงก่อนตัดสินใจ** ทุกขั้นแสดงค่าเช่า มัดจำ ค่าซัก ค่าส่ง และวันรับ/วันคืนชุด ก่อนกดจอง
3. **นโยบายร้านเก็บเป็นค่าตั้งในฐานข้อมูล ไม่เขียนตายตัวในโค้ด** ร้านจึงปรับตัวเลขได้โดยไม่ต้องแก้โปรแกรม

# ส่วนที่ 1: แนวคิดและกลยุทธ์การออกแบบ

## 1.1 แนวคิดภาพรวมของงานกราฟิกและแบรนด์

**บุคลิกแบรนด์:** สนุกสนาน เข้าถึงง่าย และน่าเชื่อถือ ร้านเช่าต้องดูเป็นมิตรกับคนที่ไม่เคยเช่า และต้องดูน่าเชื่อถือพอให้ลูกค้ากล้าโอนเงินมัดจำ

**ภาษาภาพ (Design System v2):** พื้นขาว เส้นเข้ม 1px ปุ่มชมพู และเงาแข็งที่โผล่เฉพาะตอนโต้ตอบ

| การตัดสินใจ | เหตุผล |
|---|---|
| ย้ายความเป็น neo-brutalist จาก "การตกแต่งถาวร" มาเป็น "การตอบสนองต่อการโต้ตอบ" (ปุ่มยกขึ้น 4px พร้อมเงาแข็งตอน hover) | เวอร์ชันแรกมีเส้นหนาและเงาทุกจุด หน้าเว็บจึงดูรก เวอร์ชันใหม่สงบลงแต่ยังจำแบรนด์ได้ และเงากลายเป็นสัญญาณว่า "กดได้" |
| ชมพู (`#E4487D`) ใช้กับปุ่มหลัก สถานะที่เลือก และราคาเท่านั้น ราว 10% ของจอ | ชมพูมีความหมายเดียว ผู้ใช้เห็นแล้วรู้ว่าเป็นจุดที่ต้องกดหรือดู |
| hover ห้ามเป็นสีชมพู | พื้นชมพูอ่อนหมายถึง "เลือกอยู่" ถ้าใช้ตอน hover ด้วย ผู้ใช้จะแยกสองสถานะนี้ไม่ออก |
| สีสถานะ (info / success / warning / danger) ความหมายเดียวกันทั้งฝั่งลูกค้าและแอดมิน | ลดการเรียนรู้ซ้ำ |
| เหลืองและลาเวนเดอร์ใช้กับภาพประกอบเท่านั้น | กันไม่ให้สีตกแต่งถูกอ่านเป็นสถานะ |
| ฟอนต์เดียว Noto Sans Thai ทั้งไทยและอังกฤษ ระยะบรรทัด 1.6 | ภาษาไทยมีสระบน-ล่างและวรรณยุกต์ซ้อน ต้องการพื้นที่แนวตั้ง |

**ความหนาแน่นสองระดับ ภาษาเดียว:** ฝั่งลูกค้าใช้ตัวอักษร 16px และปุ่มสูง 44px (เป้ากดนิ้วบนมือถือ) ฝั่งแอดมินบนจอใหญ่ใช้ 14px และ 36px เพื่อให้เห็นข้อมูลได้มากในจอเดียว

ค่าสี มุมโค้ง เงา และตัวอักษรทั้งหมดเป็น token ใน `app/globals.css` (Tailwind v4 `@theme`) หน้าเว็บห้ามเขียนค่า hex ตรง ๆ รายละเอียดอยู่ใน [design-system.md](../design-system.md)

## 1.2 ลำดับการปฏิสัมพันธ์ฝั่งลูกค้า

ลำดับนี้คือเส้นทางหลักตั้งแต่หาชุดจนได้เงินมัดจำคืน แต่ละขั้นส่งข้อมูลต่อให้ขั้นถัดไป

```
สำรวจชุด → รายละเอียดชุด → ตะกร้า → ชำระเงิน (checkout) → โอน + แนบสลิป
   → รอแพ็กส่ง → ได้รับชุด → ใช้งาน → ส่งคืน (กรอกเลขพัสดุ) → ร้านตรวจสภาพ → ได้มัดจำคืน → รีวิว
```

### ขั้นที่ 1: สำรวจชุด (`/costumes`)

- แบนเนอร์ค้นหาค้นได้ทั้งชื่อชุด ตัวละคร และชื่อเรื่อง มีทางลัด "เรื่องยอดฮิต" ที่คำนวณจากข้อมูลจริง (4 เรื่องที่มีชุดมากที่สุด)
- ตัวกรองมีหมวด เพศ ไซส์ สี ธีม ช่วงราคา เรื่อง → ตัวละคร (ต้องเลือกเรื่องก่อน) และ **"ว่างวันที่"** ซึ่งแสดงชุดที่ยังไม่มีคนจองไปใส่ครบทุกตัววันนั้น ไม่นับวันขนส่ง/ซัก ส่วนวันที่จองได้จริงตรวจอีกครั้งที่ปฏิทินหน้าชุด
- ตัวกรองที่เลือกแสดงเป็นชิป กดกากบาทเพื่อเอาออกทีละอันได้
- **ค้นไม่เจอ:** แสดงคำแนะนำให้ลดตัวกรอง แล้วต่อด้วยหัวข้อ "ชุดที่คุณอาจสนใจ" (ชุดคะแนนรีวิวสูงสุด 6 ชุด) ลูกค้าจึงไม่เจอหน้าว่าง
- เข้ามาจากหน้าอีเวนต์ได้ด้วยปุ่ม "หาชุดที่ว่างวันงาน" ระบบจะส่งวันที่มากรองให้เลย

### ขั้นที่ 2: รายละเอียดชุด (`/costumes/[id]`)

หน้านี้ออกแบบเป็นขั้นตอนตามลำดับการตัดสินใจจริง เพราะแต่ละขั้นมีผลกับขั้นถัดไป

| ลำดับ | สิ่งที่เลือก | ทำไมต้องอยู่ตรงนี้ |
|---|---|---|
| 1 | ไซส์ชุด (+ ตารางไซส์ วิธีวัดตัว) | วันว่างขึ้นกับไซส์ |
| 1.1 | ไซส์รองเท้า หรือ "ไม่รับรองเท้า" (เฉพาะชุดที่มีรองเท้า) | ไม่รับรองเท้า = ลดราคา |
| 2 | จำนวนวันเช่า | วันว่างขึ้นกับความยาวการเช่า |
| 3 | วิธีรับชุด (จัดส่ง / รับเองที่ร้าน) | รับเองไม่ต้องกันวันขนส่ง วันว่างจึงต่างกัน |
| 4 | วันที่จะใส่ชุด (ปฏิทิน) | ขั้นสุดท้าย เพราะต้องรู้ทุกอย่างข้างบนก่อน |
| สรุป | ไทม์ไลน์ ได้รับชุด → วันใช้งาน → ส่งคืนภายใน และตารางราคา | ลูกค้าเห็นยอดรวมก่อนกด |

**ปฏิทินแยกความหมายของวันที่จองไม่ได้ออกเป็นสองแบบ**

- **พื้นเทา "จองแล้ว":** ชุดอยู่กับลูกค้าคนอื่นจริง
- **ตัวเลขขีดฆ่า:** ชุดยังว่าง แต่ถ้าเริ่มเช่าวันนี้จะชนกับการจองถัดไป

การแยกนี้ช่วยให้ลูกค้าเข้าใจว่าทำไมวันที่ดูว่างถึงกดไม่ได้ ปฏิทินยังมีจุดบอกวันที่มีอีเวนต์คอสเพลย์ และป้ายไซส์ที่ถูกจองใต้วันที่ด้วย

**รองเท้าไม่ว่างไม่ล็อกชุด (ปรับปรุงล่าสุด):** ปฏิทินดูเฉพาะชุดหลัก หลังเลือกวันแล้ว ปุ่มไซส์รองเท้าที่ไม่ว่างจะมีป้าย "ไม่ว่าง" (แต่ยังกดได้) ถ้าเลือกไซส์ที่ไม่ว่าง จะมีกล่องให้ลูกค้าเลือกทางใดทางหนึ่ง

- เปลี่ยนไซส์รองเท้า
- ไม่รับรองเท้า
- ติ๊กยอมรับให้ร้านจัดหาคู่ใกล้เคียง (ราคาเท่าเดิม ร้านโทรคุยก่อนส่ง หาไม่ได้คืนค่ารองเท้า)

ร้านจึงไม่เสียโอกาสขายชุดเพราะพร็อพชิ้นเดียว

**เช่าแยกชิ้น:** ชุดที่ร้านเปิดเช่าแยกไว้ ลูกค้าสลับเป็นโหมด "เลือกเช่าแยกชิ้น" แล้วติ๊กเฉพาะชิ้นที่ต้องการได้ ราคาชิ้นแสดงเป็นช่วงก่อนเลือกวัน และเป็นราคาของตัวที่จะได้หลังเลือกวัน

### ขั้นที่ 3: ตะกร้า (`/cart`)

- ตะกร้าแยกตามบัญชีผู้ใช้ เก็บในเบราว์เซอร์ (localStorage)
- ทุกครั้งที่เปิด ระบบตรวจซ้ำว่าแต่ละรายการยังจองได้ไหม ถ้าไม่ได้จะบอกเหตุผลเจาะจงพร้อมปุ่มแก้ไข เช่น วันถูกจองไปแล้ว วันกระชั้นเกินไป ชิ้นที่เลือกปิดเช่า หรือรองเท้าไซส์ที่เลือกไม่ว่าง
- วิธีรับชุดเป็นของทั้งตะกร้า เพราะค่าส่งคิดต่อออเดอร์ ถ้าเพิ่มของที่วิธีรับต่างกัน ระบบจะถามก่อนเปลี่ยน
- ออเดอร์หนึ่งมีได้สูงสุด 10 รายการ

### ขั้นที่ 4: Checkout (`/checkout`)

- **เช่าครั้งแรก:** ต้องอัปโหลดรูปบัตรประชาชนที่เขียนกำกับไว้ (ร้านเก็บแค่รูป ไม่เก็บเลขบัตร) อัปโหลดล่วงหน้าในหน้าบัญชีก็ได้
- **ข้อมูลที่กรอก:** ที่อยู่จัดส่ง (หรือผู้ติดต่อถ้ารับเอง) และบัญชีรับเงินมัดจำคืน ข้อมูลที่เคยกรอกจะถูกจำไว้ให้ครั้งต่อไป
- **กดยืนยัน:** ฐานข้อมูลตรวจซ้ำทุกอย่างในฟังก์ชัน `create_booking` ถ้ามีคนจองตัดหน้าไปแล้ว ลูกค้าจะได้ข้อความภาษาไทยพร้อมพากลับไปเลือกวันใหม่

### ขั้นที่ 5: ชำระเงินและติดตาม (`/orders/[id]`)

- **ชำระเงิน:** ระบบสร้าง QR พร้อมเพย์ที่ฝังยอดไว้ ลูกค้าแก้ยอดเองไม่ได้ ยอดในสลิปจึงตรงกับออเดอร์เสมอ
- **ตรวจสลิป:** ลูกค้าแนบสลิปแล้วระบบตรวจให้อัตโนมัติ
- **ติดตาม:** หน้าออเดอร์แสดงขั้นตอน 7 ขั้น (ชำระเงิน → ตรวจสอบยอด → เตรียมจัดส่ง → จัดส่งชุด → ใช้งานชุด → ส่งคืน/ตรวจสภาพ → เสร็จสิ้น) พร้อมเลขพัสดุ รูปตอนแพ็ก และวันที่ต้องส่งคืน
- **อีเมลแจ้ง:** ระบบส่งอีเมลที่จุดสำคัญ ได้แก่ ผลตรวจบัตร จัดส่งแล้ว เตือนส่งคืนล่วงหน้า ผลตรวจสภาพและยอดหักมัดจำ และโอนคืนสำเร็จ

### ขั้นที่ 6: หลังเช่า

- ลูกค้ารีวิวได้เฉพาะรายการที่เช่าจบแล้ว รีวิวบนเว็บจึงมาจากผู้เช่าจริงทั้งหมด
- รายการโปรด, อีเวนต์ (กดสนใจ และอัปโหลดรูปจากงาน) และหน้าบัญชี (รูปโปรไฟล์ ที่อยู่ บัญชีธนาคาร รูปบัตร)

## 1.3 ลำดับการปฏิสัมพันธ์ฝั่งแอดมิน

ฝั่งแอดมินออกแบบเป็น **"คิวงาน"** ไม่ใช่รายการออเดอร์ทั้งหมด ระบบคำนวณว่าออเดอร์แต่ละใบ "ต้องทำอะไรต่อ" แล้วจัดเข้าคิว แผงขวาแสดงเฉพาะฟอร์มของงานนั้น ทำเสร็จแล้วระบบเลื่อนไปออเดอร์ถัดไปในคิวเอง

| คิว | งานในแผงขวา | เส้นตายที่แสดง |
|---|---|---|
| ตรวจบัตร | ดูรูปบัตร → อนุมัติ / ไม่อนุมัติพร้อมเหตุผล | เวลาที่เหลือก่อนออเดอร์หมดอายุเอง (แดงเมื่อเหลือไม่ถึง 3 ชม.) |
| ตรวจยอดชำระ | ดูสลิปที่ระบบตรวจไม่ผ่านอัตโนมัติ | — |
| รอแพ็กส่ง | หยิบชุดตามรหัสตัวจริง → เช็กลิสต์ของในกล่อง → ถ่ายรูป → เลขพัสดุ (หรือชื่อผู้มารับ) | "ต้องส่งวันนี้" / "ส่งช้าแล้ว X วัน" |
| **จัดหารองเท้า** (ใหม่) | โทรหาลูกค้า → บันทึกโน้ต → "จัดหาได้แล้ว" หรือ "หาไม่ได้ · คืน ฿X" | — |

## 2.3 ตรรกะการคำนวณ

ทุกสูตรด้านล่าง **คำนวณจริงในฟังก์ชันฐานข้อมูล** หน้าเว็บมีโค้ดคำนวณซ้ำ (`utils/customer/rentalPrice.ts`, `pieces.ts`, `bookingSettings.ts`) เพื่อแสดงผลเท่านั้น และต้องตรงกับฐานข้อมูลทุกบาท

### 2.3.1 วันเช่าและการล็อกชุด

```
วันคืน (end_date) = วันใส่ + จำนวนวันเช่า
ช่วงล็อกชุด        = [วันใส่ − buffer_days_before , วันคืน + buffer_days_after]
```

- `buffer_days_before` = วันขนส่งก่อนวันใส่ (รับเองที่ร้าน = 0)
- `buffer_days_after` = วันส่งกลับ ตรวจ และซัก
- ช่วงล็อกของสองการจองบน **ชุดจริงตัวเดียวกัน** ซ้อนกันไม่ได้แม้แต่วันเดียว ฐานข้อมูลบังคับด้วย exclusion constraint บนคอลัมน์ `blocked_during`
- **วันใส่ที่เร็วที่สุด:** จัดส่ง = `max(min_lead_days, buffer_days_before)` · รับเองที่ร้าน = `pickup_lead_days` (+1 วันถ้าเลยเวลาตัดรอบ)
- **ช่วงเปิดจอง:** 120 วันนับจากวันนี้ · **จำนวนวันเช่า:** 1–5 วัน
- **วันว่างของไซส์:** วันใส่ D จองได้เมื่อยังมีชุดจริงสถานะ `available` อย่างน้อย 1 ตัวที่ช่วงล็อกไม่ชนกับการจองเดิม (ฟังก์ชัน `get_unavailable_start_dates`)

**ตัวอย่าง:** buffer 1/1 วัน เช่า 3 วัน ใส่วันที่ 10 → ได้รับชุดวันที่ 9 · ใส่ 10–12 · ส่งคืนภายใน 13 · ร้านตรวจ/ซัก 14 → ชุดตัวนี้ถูกล็อกวันที่ 9–14

### 2.3.2 ค่าเช่า

**ราคาตามช่วงอายุของชุดจริงแต่ละตัว** (ราคาเดียวทุกไซส์ แต่ต่างกันตามตัวที่ได้)

| ช่วง | ราคาที่ระบบเสนอ | เข้าช่วงเมื่อ |
|---|---|---|
| ชุดใหม่ (`new`) | 50% ของต้นทุน | ค่าเช่าสะสมของตัวนั้น < ต้นทุน |
| ราคาปกติ (`normal`) | 35% ของต้นทุน | ค่าเช่าสะสม ≥ ต้นทุน (ไม่มีต้นทุน = ปกติ) |
| ชุดเก่า (`old`) | 25% ของต้นทุน | ใช้งานครบ 10 รอบ (เปิด/ปิดได้) · เช่าแยกชิ้นนับตามสัดส่วนยอดเช่า |

- ทุกราคาปัดขึ้นเป็นหลัก 50 บาท ขั้นต่ำ 250 บาท แอดมินแก้ราคาเองได้ และล็อกราคาไม่ให้ปรับอัตโนมัติได้
- "ค่าเช่าสะสม" และ "จำนวนรอบ" นับสดจากออเดอร์ที่เสร็จสิ้นทุกครั้ง ไม่มีตัวนับที่อาจเพี้ยน
- **ตอนจอง ระบบเลือกตัวที่ว่างและค่าเช่าถูกที่สุดก่อน** แล้วบันทึกราคาและช่วงไว้ในรายการ ราคาที่บันทึกแล้วไม่ย้อนแก้

**ค่าเช่าของหนึ่งรายการ**

```
ทั้งชุด:  ค่าเช่าวันแรก = ราคาของตัวที่ได้ − (ราคารองเท้า ถ้าเลือก "ไม่รับรองเท้า")
          ค่าวันเพิ่ม/วัน = extra_day_rate (ปัจจุบัน 400 บาท)
แยกชิ้น: ราคาชิ้น = (ราคาของตัวที่ได้ − ราคาชิ้นตายตัว) × ระดับชิ้น ÷ ระดับรวม × piece_price_markup_percent%
          ปัดขึ้นตาม piece_price_round ขั้นต่ำ piece_price_min · ชิ้นกำหนดราคาเองและรองเท้าเป็นราคาตายตัว
          ค่าเช่าวันแรก = ผลรวมราคาชิ้นที่เลือก ไม่เกินค่าเช่าทั้งชุดของตัวนั้น
          ค่าวันเพิ่ม/วัน = ceil( min(ค่าเช่าวันแรก × piece_extra_day_percent%, extra_day_rate) )
ค่าเช่ารวม = ค่าเช่าวันแรก + (จำนวนวัน − 1) × ค่าวันเพิ่ม/วัน
```

ระดับชิ้นคือ หลัก 3 / รอง 2 / เสริม 1 แอดมินเลือกในฟอร์มชุด ราคาชิ้นจึงลดตามช่วงเดียวกับค่าเช่าทั้งชุด

### 2.3.3 มัดจำ

| ช่วงค่าเช่า (บาท) | มัดจำ |
|---|---|
| 250 – 500 | 150 |
| 501 – 1,000 | 250 |
| 1,001 – 1,500 | 400 |
| 1,501 – 2,000 | 550 |

- มัดจำไม่ขึ้นตามจำนวนวันเช่า

### 2.3.4 ยอดชำระ

```
ยอดชำระ = Σ ค่าเช่ารวม + Σ มัดจำ + Σ ค่าซักรีด + ค่าส่ง (ต่อออเดอร์ · รับเอง = 0)
```

**ตัวอย่าง:** ชุดต้นทุน 1,800 บาท ตัวที่ได้ยังเป็น "ชุดใหม่" (900 บาท) เช่า 2 วัน ไม่รับรองเท้า (ราคารองเท้า 150) จัดส่ง EMS ค่าส่ง 60 ค่าซัก 50

```
ค่าเช่าวันแรก = 900 − 150 = 750
ค่าวันเพิ่ม    = 1 × 400 = 400      → ค่าเช่ารวม 1,150
มัดจำ          = ตามค่าเช่าเต็มชุด 900 → 250
ยอดชำระ        = 1,150 + 250 + 50 + 60 = 1,510 บาท
```

(ตัวเลขค่าส่งและค่าซักในตัวอย่างเป็นค่าสมมติ ค่าจริงตั้งในฐานข้อมูล)

### 2.3.5 หลังคืนชุด: ค่าปรับ การหัก และยอดคืนเงิน

```
วันคืนช้า    = วันที่ลูกค้ากรอกเลขพัสดุคืน (หรือวันที่นำมาคืนที่ร้าน) − วันคืน
ค่าปรับคืนช้า = min(วันคืนช้า × late_fee_per_day, มัดจำ)     (แอดมินยกเว้นได้)
ค่าเสียหาย    = Σ รายการหัก (ชำรุด / ของไม่ครบ / ซักพิเศษ)  หรือ = มัดจำทั้งหมดถ้า "สูญหาย"
ยอดคืนเงิน    = มัดจำ − ค่าปรับ − ค่าเสียหาย + ค่ารองเท้าที่ร้านหาให้ไม่ได้
```

- **เพดานยอดหัก:** ยอดหักรวมเกินมัดจำไม่ได้ ระบบปฏิเสธและให้เลือก "สูญหาย" แทน
- **สูญหาย:** ทำได้เมื่อเลยกำหนดคืนเกิน `overdue_lost_days` (7 วัน) · ชุดถูกปลดระวาง และลูกค้าถูกตั้งเป็นแบล็กลิสต์อัตโนมัติ
- **ผลต่อสถานะชุดจริง:** ชำรุดหนักหรือเล็กน้อย → ส่งซ่อม ปิดรับจองจนกว่าจะพร้อม
- **รองเท้าที่หาไม่ได้:** ค่ารองเท้าที่ร้านหาให้ไม่ได้ไม่นับเป็นมัดจำ จึงไม่ถูกหัก และคืนให้แม้กรณีสูญหาย (Step 29)
- **ยกเลิกหลังจ่าย:** ร้านยกเลิก → คืน `grand_total` ทั้งก้อน · นโยบายลูกค้ายกเลิก: ก่อนวันใช้งาน ≥ 3 วันคืนทั้งหมด ช้ากว่านั้นยึดมัดจำแต่คืนค่าเช่า

### 2.4.4 ความปลอดภัยของข้อมูล

- **Row Level Security (RLS):** ลูกค้าอ่านได้เฉพาะออเดอร์ ที่อยู่ และบัตรของตัวเอง ตารางภายในร้าน (โน้ตสมาชิก ประวัติการแบน) แอดมินอ่านได้เท่านั้น
- **เขียนผ่านฟังก์ชันเท่านั้น:** ข้อมูลสำคัญ (สถานะออเดอร์ ยอดเงิน สถานะบัตร) ลูกค้าแก้ตรงไม่ได้ ต้องผ่านฟังก์ชันที่ตรวจเงื่อนไข
- **ความลับอยู่ฝั่งเซิร์ฟเวอร์:** service role key, SMTP และ Slip2Go key อยู่ใน environment variable ของเซิร์ฟเวอร์ ไม่ถูกส่งไปที่เบราว์เซอร์
- **กันส่ง path ปลอม:** route ตรวจสลิปและหลักฐานเช็กว่า path ไฟล์อยู่ในโฟลเดอร์ของผู้ใช้และออเดอร์นั้น (กัน `..`)
- **ความเป็นส่วนตัว:** เลิกเก็บเลขบัตรประชาชน (Step 24) เก็บแค่รูป และลบอัตโนมัติตามนโยบาย

## 2.8 ข้อจำกัดที่ทราบและแนวทางปรับปรุงต่อ

| เรื่อง | สถานะปัจจุบัน | แนวทาง |
|---|---|---|
| ไฟล์ SQL Step 1–18 ไม่อยู่ใน repo | ฟังก์ชันบางตัวต้องดึงจากฐานข้อมูลด้วย `pg_get_functiondef` ก่อนแก้ | export schema ทั้งหมดเก็บเป็น migration ใน repo |
| ค่าตั้งหลายตัวไม่มีหน้าแก้ในเว็บ | ต้องแก้ใน Supabase โดยตรง (ข้อ 2.5) | ทำหน้า "ตั้งค่าร้าน" ในแอดมิน |
| ช่องทางติดต่อร้าน | ยังไม่มี LINE · ลูกค้ายกเลิกเองในเว็บได้เฉพาะออเดอร์ที่ยังไม่จ่าย | เพิ่ม LINE OA และคำขอยกเลิกในเว็บ |
| พื้นเทา "จองแล้ว" ในปฏิทิน | อาจเลื่อน 1–2 วันเมื่อการจองเดิมใช้จำนวนวันต่างกัน (วันที่กดได้/ไม่ได้ยังถูกต้องเสมอ) | ให้ RPC ส่งช่วงล็อกจริงกลับมาแทนการถอดค่าย้อนกลับ |
| พร็อพอื่นนอกจากรองเท้า | ยังไม่มีสต็อกรายชิ้น | ถ้าจะนับสต็อก ใช้หลักเดียวกับรองเท้า: ของเสริมไม่ล็อกชุดหลัก |
| dependency ที่ไม่ได้ใช้ (`stripe`, `@next/font`) | ยังอยู่ใน `package.json` | ลบออกเพื่อลดขนาดและความเสี่ยงด้านความปลอดภัย |
